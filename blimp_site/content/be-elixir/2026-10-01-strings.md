# 2026-10-01: a string index is a byte offset

Forty-four of Temper's functional tests pass, up from thirty-eight:
TypesStringRead, TypesIntLimits, TypesIntShifty, TypesListOperations,
FunctionsDefaulting and RegressionMinimalRepro.

## Why Elixir was the easy target for strings

Temper's `String` is navigated by `StringIndex`, an opaque position that only
`next`, `prev`, `step` and `String.begin` produce. Its doc comments say what
it is for a UTF-8 backend: an offset in bytes, stepping over whole code
points. An Elixir string is a UTF-8 binary, so an index is just an integer
and nothing has to be converted. `String.begin` is `0`, `s.end` is
`byte_size(s)`, and `StringIndex.none` is `-1`.

`next` reads the lead byte to know how far to step; `prev` walks back over
continuation bytes (`10xxxxxx`). One trap: Elixir's `String.length/1`
counts graphemes, and Temper's `countBetween` counts code points. The
polar bear in TypesStringRead, 🐻‍❄️, is one grapheme and four code points.

TypesStringRead now matches Temper's expected output line for line,
including `κόσμε𐆊` (a supplementary-plane code point at the end), the
polar bear, slicing with out-of-range bounds, and `indexOf`.

## The one line that differed

On the first run every line matched but one:

```
expected: Parse  2  -> 2
but was:  Parse  2  -> failed
```

`String.toInt32` trims whitespace, the way `toFloat64` does. Nothing in
`core.temper` says so; the functional test does. Integer parsing now trims
first, and has a test for it.

## Also passing now

TypesIntLimits and TypesIntShifty exercise the 32-bit wrap and the shift
operators against Temper's own expected output, including the unsigned right
shift (`TemperCore.int32(Bitwise.bsr(Bitwise.band(x, 0xFFFFFFFF), n))`),
and pass without a change to chapter 5's operator table.

**Not done:** maps (`Mapped`, `MapBuilder`), `Deque`, `DenseBitVector`,

and two tests whose generated code `mix` still refuses to compile.
