# 2026-10-01: `@actor`: a Temper object that is a process

Until now every Temper object lived in one process. The question was
whether processes could share a live, mutable object. This chapter makes
that possible as an opt-in, per class.

## A decorator in Temper core

Temper rejects decorators it does not know:

```
[-work/src/a.temper.md:3+5-10]@G: No declaration for nym`@actor`
```

`@imu` turned out to be a `MetadataDecorator` registered in the
interpreter's builtin environment. `@actor` is now one too: a symbol in
`NamesAndSymbols.kt`, a decorator next to `vImuDecorator`, and a
`keyPair` in `BuiltinEnvironment`. It only adds metadata, and only the
BEAM backend reads it, so on every other backend an `@actor` class is an
ordinary class. The probe's counter prints `1` under `-b js` as it always
did. This is a change to Temper itself, so it would go upstream with the
fork's other fixes.

## What the backend does with it

`new` becomes `TemperCore.Actor.start(Class, fn -> constructor end)`,
which starts a GenServer and runs the constructor inside it.
`TemperCore.Actor.init_self` gives the constructor its `this`: a
`%TemperCore.Actor{class, pid}` whose fields are a heap object in the new
process. Each instance method body is wrapped in
`TemperCore.Actor.run(this, fn -> ... end)`. If `this` is the current
process, that is a plain call. Otherwise it sends the closure to the actor
with `GenServer.call`, and the method runs where its fields are.
`Heap.get` and `Heap.put` on an actor reach those fields, and only from
inside it. Static dispatch, `TemperCore.call`, `class_of` and `is_a` all
work on actors unchanged.

The semantics, checked from Elixir against a translated bank
(`examples/bank/`):

```
after 1000 concurrent deposits: 1000
after transfer: ann 700, bob 300
withdraw too much: bubbled back to the caller (TemperCore.Bubble)
cycle: Panic: actor call cycle: Temper.Bank.Account is already waiting on this call
mutable argument: Panic: an argument to Temper.Bank.Account is a mutable Temper.Bank.Box, which cannot be shared with another process; make its class @imu to pass a copy, or @actor to share it
actor whose creator ended: Panic: Temper.Bank.Account actor has ended
```

- **No lost updates.** The actor takes one call at a time.
- **Errors come back.** The actor catches the raise and replies with it,
  and the caller raises it again with the original stack trace.
- **Cycles are a panic, not a hang.** Every call carries the chain of
  actors it has passed through. Calling back into one of them would
  deadlock, since it is blocked in `GenServer.call` waiting on this very
  call, so that call raises instead.
- **Only values cross.** Arguments, results and every captured value in
  the sent closure are walked. A mutable non-actor object anywhere inside
  them is refused by name. Copying it would quietly split one object into
  two.

## The lifetime bug the probe caught

My first version linked each actor to its creator and documented that it
"ends with it". The last line of the probe said otherwise:

```
actor whose creator ended: 1
```

A link only propagates an *abnormal* exit. The creator had returned
normally, so its actor kept running, and nothing would ever stop it. The
actor now also monitors its creator and stops on any `:DOWN`. The link
stays, so a crash in either one still takes the other down. A related
detail: the process starts unlinked and is linked only after the
constructor succeeds. A linked process that stops in `init` takes its
caller down instead of letting the caller raise.

## Cost

A method call from another process: 100,000 took 164 ms, 1.64 µs each,
against about 0.6 µs for a local heap update. So actors suit coarse
objects such as accounts, sessions, caches and registries, not every
small object.

## Not done

- No supervision tree. An actor lives and dies with its creator.
- Module-level mutable state is per process: an actor starts with a copy
  of its creator's globals.
- `async` inside an actor drains after each call. Nothing makes Temper's
  own `async` concurrent.
