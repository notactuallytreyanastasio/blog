# 2026-10-01: a list builder is a list, too

Thirty-eight of Temper's functional tests pass, up from thirty-four:
TypesListReduce, TypesListSorting, ClassesObjectLiterals and
ImportsFunctions.

## Two kinds of list, one set of reads

Temper has an immutable `List` and a mutable `ListBuilder`, and both are
`Listed`. A `List` is an Elixir list. A `ListBuilder` is aliased and
mutated, so it is a heap object holding an Elixir list, for the same reason
a mutable class is: every alias has to see every `add`.

The consequence is easy to miss. A function typed to take a `Listed` can be
handed either, so `Listed.get length()` cannot be `Kernel.length/1`, which
was the first translation and is what chapter 5 shipped: it would fail on a
builder. Every read goes through `TemperCore.List`, which asks for the
elements first:

```elixir
def items(%Ref{} = lb), do: Heap.get(lb, :items)
def items(list) when is_list(list), do: list
```

## What Temper's core says, and what Elixir does about it

The doc comments in Temper's `core.temper` are the specification, and they
distinguish two kinds of failure:

- `ListBuilder.add` at a position outside `0..length`, `removeLast` on an
  empty builder, and `set` out of bounds *panic*. They raise
  `TemperCore.Panic`, which nothing in Temper catches.
- `get` out of range *bubbles*: `TemperCore.Bubble`, which `orelse` can
  catch.
- `splice` clamps its index. `reduce` starts from element 0, so on an empty
  list it bubbles, through that same `get`.
- `sorted` and `sort` are stable, and Elixir's `Enum.sort/2` is stable when
  the function says `true` for equal elements, so the comparison is
  `compare.(a, b) <= 0`.
