# 2026-10-01: a library initializes itself

Every example so far began with `Temper.Lib.__temper_init__()`. Without
it, the first exported call that reads a module value fails:

```
** (ArgumentError) module-level :"Temper.Svc.tally" read before it was set
```

That trap catches every Elixir developer who uses a translated library.
Two changes from the last few chapters made it cheap to remove. Init runs
once per node, and later calls check a flag in ETS (entry 20). Every
exported function already runs through a wrapper, `Heap.entry` (entry
18). So each exported function now begins:

```elixir
def handle(n) do
  Temper.Svc.__temper_init__()
  TemperCore.Heap.entry(fn ->
    ...
```

Constructors of exported classes begin the same way, since Elixir code can
call `Temper.Lib.Account.new(...)` directly. For an actor class, the init
runs in the caller, before the actor's process starts; init is node-wide,
so either process would do. Code inside the library's own top level (an
exported function called during init) skips the check, because
`init_once` has already marked that process as running it.

```
$ mix run -e 'IO.puts(Temper.Svc.handle(1)); IO.puts(Temper.Svc.handle(2))'
req 1
req 2
```

On the GenServer benchmark (100,000 requests) the cost does not show:
263 ms, against 270 ms before. 65 of 65 functional tests pass.
