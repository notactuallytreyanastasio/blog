# 2026-10-01: the runtime's hot paths

Entry 26 left Marginalia's generated code 3x slower than the Elixir it
replaced, and named the cause as "walking strings one code point at a
time". That was half right. A profile of the segmenter
(`:tprof`, `type: :call_time`, one 11,700-word manuscript) showed that
the walking itself was not the biggest cost. The biggest cost was what
each step touched:

```
TemperCore.Heap.fields!/1     803,243 calls   9.7%
TemperCore.Heap.put/3         400,500 calls   9.0%
TemperCore.String.next/2      702,187 calls   8.2%
Process.get/2               1,205,569 calls   6.6%
TemperCore.Heap.key/1       1,204,975 calls   6.2%
...
sets:is_element/2             400,500 calls   2.1%
```

400,500 heap writes, and 398,269 of them were one `StringBuilder`
append each. A `StringBuilder` was an ordinary heap object, a map with
one field `:s`. So every appended code point read the map from the
process dictionary, updated it, wrote it back, and then ran the write
barrier: it read the nursery and checked whether the builder was young.
That is about a dozen calls to put one byte on the end of a string.

## A string needs no write barrier

The write barrier exists because an older object written during a call
may now point at a young one (entry 18). A string cannot point at
anything. So a `StringBuilder` is now a *value object*: the process
dictionary holds the string itself, not a map with the string in it.

```elixir
def new, do: Heap.new_value(:string_builder, "")
def append_code_point(sb, cp), do: Heap.put_value(sb, <<Heap.get_value(sb)::binary, code_point(cp)::binary>>)
```

`put_value/2` is one `:erlang.put`. It checks that the object exists
from what `put` returns, the old value, rather than reading it first:

```elixir
def put_value(%Ref{id: id} = ref, value) do
  case :erlang.put({__MODULE__, id}, value) do
    :undefined ->
      :erlang.erase({__MODULE__, id})
      raise ArgumentError, "#{inspect(ref)} is not an object in this process"

    _ ->
      nil
  end
end
```

A value object is still a `%TemperCore.Ref{}`, so aliasing works as
before. `collect`, `export` and `import` don't care what shape the stored
term has, so they needed no change. New tests check all three, check
that the nursery frees an unreachable builder, and check that a stale
builder raises without leaving a key behind.

## Three smaller ones

- **`Heap.get` and `put` call `:erlang.get` and `:erlang.put`**, not
  `Process.get` and `Process.put`. The wrappers cost a call each, and
  these run on every field access. `key/1` is gone too: the key is built
  in place.
- **`TemperCore.int32` returns an integer already in range as it is.**
  It used to build two binaries on every `+`: `<<v::signed-32>> =
  <<x::32>>`. Now a guard clause handles the common case, and the
  existing overflow tests still pass. The same change went into `int64`.
- **`String.next/2` is one binary match.** It used to call `byte_size`,
  then `:binary.at`, then a width function. Now a pattern that skips `i`
  bytes reads the lead byte, and its guard picks the width.

## Before and after

Marginalia's bench (`bin/temper-verify bench`, median of 15), run with
the runtime from this chapter swapped in:

```
                                       before    after    Elixir
word diff, 2,000-word section           14 ms    13 ms     4 ms
paragraph diff, 60 paragraphs           22 ms    13 ms     8 ms
sentences reflow, 5,400 words            8 ms     4 ms     2 ms
PDF page reflow, 400 lines               3 ms     2 ms    11 ms
segmenter, 11,700-word manuscript       68 ms    53 ms    20 ms
```

All four of its equivalence harnesses still agree with the original
Elixir on every input. The segmenter's profiled total went from 772 ms
to 374 ms under tracing.

## What is left

The segmenter's profile no longer has a dominant cost. What remains is a
call per code point: `has_index`, `get`, `next` and an append. Each is
about 0.03 µs, and there are 700,000 of each. Two changes would remove
most of them:

- **In the backend:** inline the string primitives into the generated
  code, so that walking a string is a binary match in the generated
  function itself.
- **In Marginalia's Temper:** append runs with `appendBetween` instead of
  appending a code point at a time.

The word diff is still 3x. Its time goes into the Myers loop itself,
not the runtime.

65 of 65 functional tests pass, as do temper-core's 96 tests.
